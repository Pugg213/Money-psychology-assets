# Native asset transfer: local bytes to connected GitHub

The GitHub connector **does support binary blobs**: `create_blob` takes `content` as base64 and `encoding="base64"`. A local path is not its input. This is a transfer step, not a reason to regenerate art or assert that GitHub does not support images. In a runtime with a working local-execution-to-connected-tool bridge, no separate GitHub token or direct shell network is needed. The presence of create_blob alone does not establish that bridge.

1. Retain the exact native generator input prompt before calling it, real returned file reference and generation ID when available. Preserve available output bytes immediately. If the local source is no longer present, materialize the actual tool-reported file ID with Library's supported file materialization workflow. Never invent a source reference. The November 8 incident recovered both original PNG and final JPEG by the actual recorded file IDs.
2. Save the unchanged original PNG and permitted final JPEG locally; inspect the final JPEG. Run `python scripts/read_asset_base64.py /absolute/existing/image.png --offset 0`. It returns a bounded JSON record containing `data`, `next_offset`, `total_characters`, hashes and byte size. For files longer than a chunk, repeat at the returned next_offset until complete. The helper handles both PNG and JPEG and never draws, converts or uploads.
3. In the code/tool orchestration runtime, parse the tool stdout as JSON, retain the strings in a variable, concatenate `data` in offset order, and check every record's hashes/size and total length. Never print a whole image base64 into user-visible prose or depend on a truncated full-file tool result. A tool stdout limit was observed during the repair; chunks stay <=12000 ASCII characters so each JSON result fits the observed execution output limit. The helper enforces this bound; request a sufficient max_output_tokens (13000 was tested here).
4. From that **same orchestrator**, call connected GitHub `create_blob({repository_full_name:"Pugg213/Money-psychology-assets",content:assembled_base64,encoding:"base64"})`. Compare its returned SHA to the helper's independently computed Git blob SHA. Do this separately for original PNG and final JPEG. Do not pass a local path as blob content. Do not use Python requests or shell git push without an authorized connection.
5. Add the actual blob SHAs to a fresh Git tree at immutable unique `editorial/originals/...png` and `telegram/...jpg` paths. Complete ledger/article/queue consistently in one commit against the current main head. Re-read and verify server preflight source/JPEG SHA, size and original-source evidence. Independent review is still mandatory before queued.

If the run's actual tools cannot retain values across local execution and connected tool calls, record that precise missing orchestration capability, the real file IDs and completed source work in the same draft. Do not falsely report that GitHub itself lacks binary support or mark uploaded before read-back. The pipeline may resume exact files from another supported runtime; the operator is not asked to regenerate or manually upload them. Tool availability in a future scheduled runtime must be observed rather than assumed.

Verified November 8: original PNG 2196499 bytes -> Git blob `79d7660128c88d2bfa0e895fa1ef5c3dedaabccd`; final JPEG 306804 bytes -> `129a223564bf3b28d8ae77ac75f38113cb5a3c03`. Both SHA256 values matched the preparation run's previously saved checkpoint. No replacement cover was generated.


## Capability gate and recovery evidence (November 10)

Before creating new artwork, identify the actual, currently exposed path from generated bytes to the authorized connected GitHub call. Local container execution, Composio remote execution and the connected GitHub service may be separate filesystems and runtimes. A local pathname, a saved file ID, a written runbook and a successful helper unit test are not evidence that bytes can cross those boundaries.

- Inspect the live tool schemas. A connected `create_blob` call requires the complete base64 string, not a pathname or an opaque file ID. A file-parameter action may receive a mounted file only when its schema explicitly supports that parameter. Never improvise an unsupported tool, URL or file-resolution action.
- Verify the bridge using an existing approved binary as a read/encode/upload/read-back round trip without changing any Git reference, queue entry or publication. Compare the returned Git blob SHA and reconstructed SHA256/length with the original. A small text upload alone does not prove that a full PNG can be transferred. Record the actual runtime and successful operations; do not present a hypothetical route as tested.
- When the existing original is missing from the current filesystem, use Library materialization only if that capability is actually exposed and supports the recorded ChatGPT file reference. The instruction in step 1 is conditional, not a promise that every scheduled runtime has Library access. Do not substitute an unrelated file service, regenerate the existing cover, or search unrelated private files.
- If no functioning byte bridge or original-file retrieval exists, preserve the current canonical draft and exact checkpoint. Report `native_asset_transfer_unavailable` or `native_source_retrieval_unavailable` with the missing capability and the real file IDs/hashes. Do not spend another generation on an already-created cover, set `github_uploaded=true`, fabricate provenance, or count the date toward reserve.

On November 10 the saved November 17 original SHA was absent from GitHub and its recorded local path was absent from the repair runtime. This identifies an unresolved transfer/retrieval boundary, not a GitHub binary-format limitation and not evidence that the original was never generated. The preparation task's disabled state is a separate operational fact; empty `requires_user_action` output does not establish its cause.



## Verified bridge repair: November 13

The former 500000-character default reproduced a truncated, non-JSON execution result. The helper now defaults to and enforces at most 12000 base64 characters per call. Keep bytes inside the orchestrator, verify source metadata and contiguous offsets, then pass the assembled base64 directly to the authorized connected `create_blob`. Never print the encoded image. Independent offset reads may be batched; assemble in numerical offset order.

A complete transfer of the recovered November 17 PNG (2383565 bytes, blob `820cf8fbe61456f70bc1f131cfdc5693efa393d4`) and JPEG (358343 bytes, blob `9b091bfb7c01d923aa04dfefb97b3ef9f62218f1`) succeeded in this host and matched the prior checkpoint hashes.
