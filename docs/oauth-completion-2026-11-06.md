# Закрытие оставшихся проблем Money Psy Telegram MCP — 2.5.0

После аудита 2.4.0 проверен настоящий успешный OAuth-обмен внутри среды Vercel. Настроенный токен бота не выводился в журнал, код, артефакты или ответы модели. Отправки, удаления, отметки прочтения и изменения Business-чатов не выполнялись.

## Установленные причины

1. Прежний OAuth действительно принимал уже использованный authorization code и refresh token. Успешный вход, выдача access token, вызов MCP и refresh были подтверждены до изменения реализации. Отсутствие replay protection установлено реальным повторным запросом.
2. Подключение Business существовало, но хранилище не содержало ни одного chat/message record и ни одного forget marker. Прежние ответы также показывали 0 чатов; документально подтверждённой потери чата нет. Один подключённый аккаунт не означает один наблюдаемый чат. Telegram не возвращает список выбранных пользователем чатов или старую историю.
3. Старые generated deployment URLs представляют дополнительный OAuth issuer с тем же ключом подписи. Перенести только код на основной адрес недостаточно: старые URL необходимо закрыть Deployment Protection.
4. Независимый просмотр новой реализации выявил две ошибки предельной длины формы: чрезмерные redirect metadata и дублирование Unicode state в hidden fields. Обе воспроизведены отдельными тестами до исправления.

## Исправления

- OAuth discovery, DCR, форма входа, выдача кода и refresh выполняются из локального, проверяемого исходника. Runtime не обращается к прежнему OAuth deployment.
- Сохранены формат HMAC, resource audience, `client.jti` и совместимость существующих подписанных клиентов/токенов. Права не расширяются при refresh.
- Формы привязаны к HttpOnly/Secure/SameSite cookie и подписанным параметрам; форма и код потребляются однократно. PKCE S256, client, redirect, scope и resource проверяются до потребления кода.
- Replay barriers записываются в private Blob create-only. Параллельный повтор не выдаёт второй комплект токенов. Сбой хранилища закрывает выдачу, не раскрывая внутреннюю ошибку.
- Каждый refresh выдаёт новый refresh token. Повтор старого отзывает refresh family, включая потомков. Уже выданные access tokens сохраняют обычный срок до одного часа.
- В хранилище replay нет plaintext токенов: используются SHA-256 пути и expiry metadata. Истекшие use markers очищаются штатным cron; revocation markers сохраняются консервативно.
- DCR metadata ограничены до выдачи непригодного клиента. Форма передаёт один подписанный request вместо дублирования всех параметров. Размер проверяется до выдачи формы.
- Пустой Business-список возвращает понятный `waiting_for_first_business_message`; выдуманные ID и искусственные личные сообщения для его заполнения не создаются.
- Runtime закреплён на Node 22.x вместо автоматического перехода на будущие major-версии.

## Проверка

Локально: **270 passed, 0 failed, 0 skipped**, включая независимые проверки OAuth, конкурентного replay, CSRF, PKCE, scope, storage failure, Unicode формы и существующих 60 функций. Отдельная проверка кода не выявила дополнительного обхода client/PKCE/scope или refresh-family logic после исправлений.

Скрипт `mcp-server/scripts/server-integration-check.mjs` исполняется только явно в среде этого Vercel-проекта. Он проверяет настоящую авторизацию, обмен кода, MCP-доступ, refresh, replay и совместимость с зашифрованным краткоживущим legacy fixture. Fixture удаляется после проверки; секреты и private IDs не печатаются. Итог действующего развёртывания фиксируется в `oauth-completion-live-2026-11-06.json`.

## Границы

Обнаруженные программные дефекты и отсутствие фактического события — разные вещи. Без нового настоящего Telegram Business события нельзя подтвердить приём сообщения реального выбранного чата. Недостающие права на Business gifts нельзя выдать со стороны сервера. Полное отображение и выполнение всех Telegram мутаций не доказывается имитацией; публикация проверяется по реальным подтверждениям штатного конвейера.

Исторический журнал использования токенов прежнего stateless issuer восстановить нельзя. Действующий legacy refresh принимается при первом локальном обмене, затем участвует в ротации и защите от повторов. Старые публичные issuer endpoints должны оставаться закрыты.

Основания: [OAuth Security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), [Vercel Standard Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication), [Telegram Bot API](https://core.telegram.org/bots/api).
