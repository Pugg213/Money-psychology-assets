# Независимое финальное ревью Money Psy server 2.6.2

Дата: 13 ноября 2026. Reviewer: `/root/server_final_review`.

**Вердикт: проверенные исправления одобрены для интеграции. Блокирующих дефектов в рассмотренном объёме не осталось.** Это одобрение кода и локально проверенных сценариев, не свидетельство успешного deployment, работы реального Blob или будущего автоматического цикла.

## Что проверено

Прочитаны предыдущие блокирующие findings в `cf3bbfef9179/server-review.md`, текущие полные `business-store.js`, `audience-core.js`, `audience-service.js`, `audience-store.js`, изменения daily handler, version strings и связанные тесты. Исходники автора не изменялись. Проводились только локальные проверки с синтетическими данными и preload, блокирующим сетевые обращения.

1. **Повтор после частичной записи Business.** Индекс восстанавливается из канонической записи сообщения, а не из устаревшего повторно доставленного payload. Повтор не уменьшает новые временные отметки и не подменяет актуальное имя устаревшими сведениями.
2. **Гонка индекса с delete/forget/retention.** Версия chat record читается до зависимых message/forget records. Все три пути удаления изменяют тот же CAS key; физического удаления этого ключа при forget больше нет. Если старая запись индекса успела первой, последующее изменение очищает её. Если удаление завершилось раньше, stale CAS отвергается; повтор читает зависимости заново и видит tombstone/cutoff. Отдельно проверены отсутствующий и существующий индекс, а также старый snapshot source, уже прочитанный перед завершением удаления.
3. **Сохранение незатронутых метаданных.** Источники четырёх полей индекса записаны по message ID. Удаление старого сообщения, не являющегося источником индекса, сохраняет более новый индекс. При затронутом или старом индексе без provenance очищаются имя и время, а возможность ответа по недоказанному старому окну не сохраняется. Retention оставляет pending marker, чтобы повторить неуспешную очистку индекса.
4. **Конфликт обсуждения.** Подтверждённый thread mapping и прямой modern/legacy forward source теперь должны совпасть. Противоречивый комментарий отклоняется до новых mapping/event writes. Разделение по каналу и группе сохранено.
5. **Диагностика и maintenance.** Диагностика читает membership, privacy и update routing, но оставляет `delivery_verified:false`. Private maintenance receipt описывает наблюдённый результат handler; отсутствие receipt не трактуется как доказательство отсутствия запуска. Ошибка записи receipt не подменяет результат snapshot. Нового sender или ослабления Business permissions в проверенных изменениях нет.

## Дополнительная проблема, найденная и закрытая в этом ревью

Обнаружено отдельное окно ошибки: saveMessage проходит начальный forget check; параллельный forget завершается; запаздывающая source mutation создаёт старые body/label; следующее чтение chat index падает до проверки marker. До доработки независимое воспроизведение вывело `raw_source_retained:true` при `visible_message:null` и `visible_chat:null`.

Автор восстановил проверку forget и очистку source **непосредственно после source mutation, до обращения к индексу**, сохранив проверку внутри CAS. После этой правки тот же независимый сценарий завершился без ошибки и с `raw_source_retained:false`; public reads остаются null. Это закрывает подтверждённую регрессию порядка операций. Полная атомарность нескольких Blob objects из этого не следует.

## Существенные границы

- Это согласование индекса и восстановление после проверенных сбоев, **не межобъектная транзакция**. Падение процесса сразу после source write либо недоступность marker/redaction могут оставить скрытую запись до предусмотренного восстановления. Нельзя обещать отсутствие физически оставшихся данных при любом прерывании на произвольной инструкции.
- Служебный fence сохраняет numeric chat ID и generation; это минимальный tombstone без имени, текста и времени сообщения, но не полностью обезличенная запись. Не следует называть его «неперсональным» или обещать физическое удаление всех идентификаторов.
- При очищенном legacy/затронутом индексе часть метаданных временно недоступна до нового пригодного события. Это консервативный отказ использовать неподтверждённые сведения для ответа, а не восстановленная полная история.
- Mapping не восстанавливает сообщения, которые Telegram не доставил боту, и ранее неизвестные ветки. Общая история обсуждений не доказана.
- Семь дат maintenance — предел чтения, не общий срок хранения всех maintenance/mapping objects. Автоматического удаления всех таких старых объектов в проверенном коде нет.
- Реальные delete/forget, записи private Blob, Telegram mutations, OAuth exchange, deployment и клиентское отображение этим ревью не выполнялись. Mock/CAS adapter не заменяет live проверку SDK и storage service.

Итог: прежние два P1 и дополнительно воспроизведённое окно source cleanup закрыты в проверенных сценариях; дальнейшая интеграция допустима с указанными границами и отдельной проверкой окончательного full suite/deployment.
